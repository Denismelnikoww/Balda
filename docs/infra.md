## Реляционные СУБД

| Сервис                  | СУБД           | Обоснование требованиями                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `identity.credentials`  | **PostgreSQL** | Строгая схема для `Owner`/`Connection`/`Mandate`; связи owner→connection→mandate - это классические FK-отношения; критичны транзакции при выдаче/отзыве мандата (нельзя «наполовину отозвать»). Нужны уникальные ограничения (owner+provider) и аудит-поля. Документная СУБД не даёт нужных инвариантов на связях, а гибкая схема тут вредна - модель стабильна и чувствительна к безопасности. |
| `campaign.plan`         | **PostgreSQL** | Ядро с состоянием саги: `ActivityPlan`↔`PlanStep`↔`SagaState` - строгие связи и транзакционная согласованность шагов (переход состояния шага и запись в outbox - атомарно). Нужны блокировки на уровне плана при конкурентных `start/pause/cancel`. Требование «таймеры шагов с точностью до минут» → индексы по `dueAt` и эффективные range-запросы.                                           |
| `delivery.integrations` | **PostgreSQL** | Идемпотентность через уникальный `IdempotencyKey` + транзакционная запись `Action` и outbox-события в одной транзакции - это ровно реляционный кейс (уникальные ограничения, атомарность). `ProviderRateLimit` - счётчики с условными обновлениями.                                                                                                                                             |
| `billing.notification`  | **PostgreSQL** | Деньги: `Payment`/`Subscription` требуют строгой схемы, уникальности `paymentId`, транзакций при смене статуса подписки. Финансовый аудит и целостность - не место для гибкой схемы.                                                                                                                                                                                                            |
| `behavior.profile`      | **PostgreSQL** | Профиль и паттерны имеют стабильную структуру, но главное - нужны оконные/агрегатные запросы по временным рядам паттернов (`ActivityPattern` по окнам), что PostgreSQL делает нативно. Документная СУБД тут не даёт выигрыша: профиль читается целым, но паттерны агрегируются.                                                                                                                 |

## Кэш 

| Для чего                        | Сервис                                                                    | Обоснование                                                                                                                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Кэш резолва мандатов            | `delivery.integrations` (потребитель) + `identity.credentials` (источник) | Требование из Шага 2: resolve мандата **< 50 мс p99** в горячем пути каждого действия. Поход в БД на каждое действие не уложится. Кэш с TTL = сроку жизни мандата + инвалидация по событию `MandateRevoked`. |
| Короткоживущие блокировки шагов | `campaign.plan`                                                           | Защита от двойного исполнения шага при at-least-once (`SET NX` с TTL) - классический кейс «бронь на 15 минут» из таблицы.                                                                                    |
| Rate-limit счётчики             | `delivery.integrations`                                                   | Атомарные `INCR`+`EXPIRE` для скользящего окна по провайдеру - быстрее, чем считать в БД на каждый вызов.                                                                                                    |

## Брокер сообщений

**RabbitMQ - команды и очереди задач:**

- `ActionRequested` из `campaign.plan` → `delivery.integrations` - это команда (одному исполнителю, с подтверждением, retry, DLQ). 
- Нужна маршрутизация по типу действия (commit/message/ticket/email) → routing keys → разные очереди адаптеров. Падение одного адаптера не блокирует другие.
- Per-message ack/requeue и DLQ - критичны для саги Plan (retry шага).

**Kafka - лог доменных событий:**

- `ActionSucceeded`/`ActionFailed`/`CommitCreated`/`MessageSent`/`StatusChanged`/`TicketUpdated` - **несколько независимых потребителей**: `campaign.plan` (сага), `behavior.profile` (паттерны). Партиции по planId
